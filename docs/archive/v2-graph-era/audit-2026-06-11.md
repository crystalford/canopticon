# Canopticon — Gap audit, 2026-06-11

Three independent passes through the codebase against the spec v2.5 + the Feels Like Brief + the prototype. Findings synthesised below by priority. Built so the operator can scan it on a phone, pick the next move, and have file paths to hand to the build side.

## TL;DR — what to fix in order

1. **The drafter skips the independent judge.** Trust hole. (Section 3.1)
2. **Cloudflare Queues + Async Batch + Durable Object WebSocket** isn't wired — the spec v2.5 Part 22 stack. The visible symptom is that you'll keep seeing slow / spotty extraction under bulk load. (Section 2.1)
3. **Live progress narration is missing** everywhere a background process runs — extraction, record-building, faces. The events are logged; nothing renders them. (Section 4.1)
4. **Record-building Phase 2 is stubbed.** Brave Search returns; nothing fetches the pages it finds. (Section 4.2)
5. **`/briefs/:slug` is still live.** Spec v2.5 deprecates Briefs entirely. (Section 5.1)
6. **Studio's still mounted.** Spec v2.5 Part 24 says the destination dies. (Section 5.2)
7. **Two public forms require JavaScript.** Confirm dialogs are inline `onsubmit`. (Section 6.1)
8. **JSON-LD on most index pages is missing.** GEO win that's free. (Section 6.4)

Everything else below is real but lower-stakes polish.

## 1. What's actually working (so we don't lose the wins)

- **The fabric is correct.** Same URL, two modes; one page renderer handles entity / event / theme. Mode toggle is server-rendered.
- **Auth + permission layers** ship and verify (PR 1). Anonymous and operator views diverge at `/` and through inline affordances.
- **Two-pass extraction** (Gemma 4 bulk + gpt-oss-120b hard) ships with aboutness edges and tolerant verbatim matching. The structural fix from the day before yesterday is in place.
- **Parallel chunk waves at concurrency 4 + smaller (3000-char) chunks + tighter cron drain (4 docs/min)** ship — fits inside the 25s per-call ceiling.
- **The settle gate runs in order**: extraction completes → L1 surfacing → theme-surfacer → autoseed-pages → proposer → draft-reading.
- **Proposer is LLM-driven** (spec Part 7 compliant). Reads typed graph + open threads. Novelty-filtered.
- **buildBrief uses the independent judge** (Qwen, different family from every generator role). Spec Part 8 + Part 10 #4 satisfied for the briefs path.
- **Faces (Part 24)** ship — thread / script / meme / chapter pre-render on signing via `generateAllFaces` in waitUntil. Per-face re-render affordance. Status states honest (queued / rendering / ready / failed). Server-rendered `<details>` (no JS).
- **Intent badges (Part 5)** ship — seven epistemic stances, drafter classifies, badge renders on signed pages + investigations cards + OUT drafts.
- **Inquiry threads** are first-class — durable, status lifecycle, fed into proposer.
- **Theme surfacing** ships — convergence threshold (3+ contradicting from distinct sources), writer names the received account, theme node + page + themes row upserted.
- **Empty-state shape blocks** ship on Topics, subject pages, investigations — explain what fills each section. (One subject-page gap remains; see 6.3.)
- **Operator affordances inline** on `/library` (Extract / Re-extract), `/s/:slug` thin Records (Expand), signed mode (Edit / Discard).
- **JSON-LD on home + brief + subject pages.** WebSite + Organization on home; per-content-type on briefs; per-kind on subject pages.

## 2. The architectural gap (Part 22)

### 2.1 No Queues, no Async Batch, no Durable Object WebSocket
**Status:** deferred — the comment in `digestion.ts` says so. Spec calls it required.
**Impact:** ceiling on extraction throughput. The current parallel-waves approach (within-doc concurrency 4) is a step in the right direction but doesn't meet the spec benchmarks: 5000-word doc < 60s, batch of 10 ≤ single, full corpus < 20min.
**What's missing concretely:**
- No `queue` binding in `wrangler.toml` and no Queue producer/consumer code.
- No `env.AI.run(model, {requests:[...]}, {queueRequest: true})` calls anywhere — the Async Batch API exists in `@cloudflare/workers-types` (verified) but the codebase uses synchronous per-chunk calls.
- No Durable Object class declared. Live extraction log streams over websocket per spec; current code only writes `orchestrator_events`.
- No dual-resolution chunking. `digestion.ts:95–112` comment acknowledges the spec wants bulk ~512 tokens and hard ~1500–2000 tokens; current code uses 3000 chars for both passes.
**Why it's parked:** every piece requires the operator's Cloudflare account to (a) create the queue, (b) declare the Durable Object class + migration. Deploying with these bindings before the queue/DO exist on the account would break deploy.
**Next move:**
1. Operator creates a Cloudflare Queue called `canopticon-extract`.
2. Operator declares a Durable Object class binding for the extraction-log WebSocket (single instance).
3. Code wires queue producer (per chunk message) + consumer (calls AI Async Batch) + DO that fans the events back to a connected client.
**Files to touch:** `wrangler.toml`, `packages/api/src/index.ts` (DO + queue handler exports), `packages/api/src/graph/lib/digestion.ts` (route bulk pass through Queue), new `packages/api/src/graph/extract-do.ts` (DO class), new `packages/api/src/graph/lib/extraction-log.ts` (event → DO broadcast helper).
**Benchmark tests:** an integration test that posts a 5KB doc and asserts complete<60s. Run against the live AI binding.

### 2.2 No live extraction log
**Status:** related to 2.1 but worth calling out separately. Even without Queues, the extraction events that get written to `orchestrator_events` are not surfaced live anywhere — the operator polls `/v1/admin/runtime` to see them. Spec demands a live log narrating every step.
**Cheapest win without DO:** add a simple SSE endpoint on `/v1/extraction/log?since=<iso>` and a thin no-JS-required polling page at `/op/library/:slug` that refreshes every 2s. Not the spec ideal but bridges the gap until DO ships.

## 3. Trust gaps (spec hard constraints)

### 3.1 The signed-reading drafter doesn't call the independent judge
**Status:** broken. **This is a hard spec constraint** (Part 8 + Part 10 #4).
**Where:** `packages/api/src/graph/lib/draft-reading.ts:329` — `page_claims` rows stored with `judge_pass=1` hardcoded. `buildBrief` correctly calls `judgeClaim` per-claim. `draftOne` doesn't.
**Symptom:** the operator sees a signed reading in OUT marked "verified" but only the verbatim-substring check has run — no independent model has confirmed the quote supports the claim. The firewall (no unattributed assertion silently rendered as fact) is enforced; the *judge* (does the source actually support the claim?) is not.
**Fix:**
1. Mirror the buildBrief verification loop — collect verified claims, call `judgeClaim` per-claim (Qwen, different family), persist `judge_pass` and `judge_notes`.
2. Refuse to mark `signed_status='draft'` if too many claims fail judgment (spec says "every load-bearing claim").
3. The signed page renderer already shows verified/killed counts — the killed list expands to include judge-failures too.
**Files:** `packages/api/src/graph/lib/draft-reading.ts:225–329`, `packages/api/src/graph/lib/briefs/pipeline.ts:166–213` (reference implementation).

### 3.2 Buildbrief judge calls aren't parallelized
**Status:** not a correctness issue but a perf one. A brief with 30 verified claims = 30 sequential judge calls.
**Fix:** parallelize via `Promise.all` with concurrency 5, or batch 5–10 claims per judge call.

## 4. UX gaps (the Feels Like Brief contract)

### 4.1 Live progress narration is missing
**Status:** the spec's most consistent demand and the codebase's most consistent miss. Three specific instances:

**(a) Record-building.** Operator clicks "Expand this Record" → POST `/op/records/:slug/expand` → redirect to `/s/:slug?expanding=1`. The renderer never reads the `expanding=1` flag. No banner. No live narration. Brave Search fires in `waitUntil`; events log to `orchestrator_events`; the operator sees the static page they already saw.
**Fix:**
1. Subject-page renderer reads `?expanding=1`. When set + operator-logged-in, render a banner: `"Building this Record — searching for {label}..."`.
2. Poll `/v1/records/:slug/expand-status` every 2s (no JS-required-to-read: the banner shows whatever state the *first* render found, polling is a progressive enhancement).
3. `/v1/records/:slug/expand-status` reads recent `orchestrator_events` and returns the latest narration ("Found 6 sources… Fetching 3 of 6… 3 facts added.").
**Files:** `packages/api/src/public/render/subject-page.ts` (banner render), new `packages/api/src/admin/expand-status.ts` (polling endpoint).

**(b) Faces in rendering state.** Operator signs a reading → faces queue → operator visits signed page. Each face shows as a `<details>` block with status="rendering" or "queued". Re-render completes; the operator only sees it after a page reload.
**Fix:** Same pattern — poll `/v1/pages/:id/face-status` every 2s, swap the body inline. Server-rendered first paint is honest; client poll is enhancement.

**(c) Extraction.** No live view. The operator has to dig into `/v1/admin/runtime` to see how a re-extract is going. Spec Part 22 demands a live log.
**Fix:** combined with 2.1 / 2.2 — single log surface, multiple sources of events.

### 4.2 Record-building Phase 2 (fetch + extract) is stubbed
**Status:** `record-builder.ts:88–98` — comment explicitly says "for now we record the discovered sources as orchestrator_events"; no fetch / no extract.
**Symptom:** clicking "Expand this Record" finds sources but doesn't add anything to the graph.
**Fix:**
1. After `braveSearch` returns N results, for each: `fetchWithTimeout(url)` → strip HTML → pass to `createAndExtract(env, userId, bytes, filename, mime, size)` — which already runs the typed-extraction pipeline.
2. Surface the per-source progress through the same event stream that powers 4.1.
**Files:** `packages/api/src/graph/lib/record-builder.ts:88–110`. Reuses `createAndExtract` from `operator/routes.ts` and existing extraction infra.

### 4.3 Two public forms require JavaScript
**Status:** `subject-page.ts:381` (Discard signed reading), `investigations.ts:289` (Re-extract all) use `onsubmit="return confirm(...)"`. Confirmation requires JS.
**Fix:** POST → intermediate confirmation page → POST (the same pattern the spec uses everywhere else). Or accept this is acceptable degradation for operator-only affordances and document.

### 4.4 The disabled "Expand this Record" button doesn't communicate state well
**Status:** button is rendered with `cursor:not-allowed; opacity:.6` — looks broken. Should clearly say "BRAVE_SEARCH_API_KEY not set" or render as enabled (the click still fires the search-skip path and emits the right event).
**Fix:** the current PR makes this button live (POSTs to the real endpoint). The "disabled" version was from an earlier commit. Verify after deploy that the button is enabled and rendered cleanly.

## 5. Surface drift (spec vocabulary + structure)

### 5.1 `/briefs/:slug` still publishes pages
**Status:** spec v2.5 Part 1 says Briefs is DEPRECATED. The route still serves a citable page. The Investigations index lists them in a "legacy briefs" block.
**Decision needed:** Operator hasn't said whether to (a) leave legacy briefs published (operator's existing public links don't break) or (b) deprecate the URL and redirect to nothing. Recommendation: leave URL serving (URL stability is valuable for citations) but stop showing them in the Investigations stream once any fabric-era reading exists.

### 5.2 Studio's still mounted
**Status:** spec v2.5 Part 24: "Studio is NOT a destination." But `/op/studio` GET 302→/ (correct), AND POST endpoints `/op/studio/skeleton` + `/op/studio/compose` are still wired (operator/routes.ts:935–1060). The screen module `screens/studio.ts` still renders.
**Fix:** delete the POST handlers + screen module. Faces-on-signing replaces what Studio offered. Skeleton + compose logic can be inlined into the face renderer if anything's still wanted.

### 5.3 "Wiki" still appears in one code comment
**Status:** `subject-page.ts:149` comment says `// NEUTRAL MODE — the wiki view, rendered from the graph`. Operator was explicit about retiring this word.
**Fix:** rename the comment. ~30 seconds.

### 5.4 Arrangement types stored but never visually applied
**Status:** briefs have `content_type` (definition / timeline / comparison / FAQ / stat-roundup / entity-profile / claim-table / etc.). All render as prose. Spec Part 5 says each arrangement type has a visual language.
**Fix:** per-type layout in `brief.ts:113`. Highest-value first: claim-table (real `<table>` markup), FAQ (`FAQPage` with `mainEntity`), stat-roundup (`<dl>` of figures). Pure render-side; data already there.

### 5.5 `/search` is a placeholder, but home JSON-LD's SearchAction points to it
**Status:** `home.ts:175` SearchAction target is `/search?q={query}`; `/search` route serves `renderPlaceholder`.
**Fix:** either build the search surface or drop the SearchAction from the JSON-LD until it exists.

### 6.2 Empty states still incomplete
- **`/s/:slug` with NO signed reading** is silent — no copy explaining that signed readings appear after the auto-drafter runs. (The reverse case — signed reading exists with thin facts — is handled.)
- **Topic hub with no pieces** silently omits the section header. Add an honest empty state.

### 6.3 Typography violations
Feels Like Brief: "no 11px labels on important information." Multiple kickers / chips / labels in `subject-page.ts` and `out-stream.ts` render at 10–11px. Audit and bump to 12px where the label carries operator-action context.

### 6.4 Surfacing L2 is manual-only
Spec Part 17 describes L2 as "rare, deliberate" — could legitimately stay manual. But the trigger is buried inside `/op/synthesis/deep` POST and the operator may not know it exists. Either:
- Auto-trigger L2 after the settle gate (slow, expensive, but ambient)
- Surface a clear "Run L2 analysis" button on OUT
**Decision needed.**

### 6.5 Canada-hardcoded seed data
`admin/seed-data.ts` references Carney, BoC, OSFI, B-20 throughout. This is **seed data for demonstration**, not architecture — leave it. Production architecture (Brave Search, extraction pipeline) is correctly jurisdiction-agnostic.
